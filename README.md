# Задание 1. Разделение проекта Mesto на несколько микрофронтендов. 

Реализовано первые 2 уровня, что обязательно для сдачи проекта.

### 1. Детальное ознакомление с кодом проекта

##### Структура проекта

Основные файлы и директории проекта:
- `./src/index.js` - основной файл, точка входа в приложение с компонентов App
- `./src/index.css` - основной файл стилей приложения
- `./src/blocks` - css стили компонентов приложения
- `./src/components` - React компоненты приложения
- `./src/contexts` - хранит файл React контекста
- `./src/images` - изображения и иконки приложения
- `./src/utils` - общие функции нашего приложения, `api.js` - класс для работы с запросами к серверу и `auth.js` набор функций для работы с авторизацией и аутентификацией пользователя
- `./src/vendor` - css стили содержащие сторонние ресурсы, шрифт и стили нормализации для разных браузеров

##### Компоненты и модули
Компоненты высшего уровня: \
Основная структура страницы формируется в `App.js`. 
Также на каждой странице присутствует `Header.js` и `Footer.js`. 
Основная часть страницы меняется.

Взаимодействие с дочерними компонентами: \
Почти вся логика отображения соответствующих компонентов сосредоточена в `App.js`.
В этом месте в зависимость от url формируется основная часть страницы  - `Main.js`, `Register.js`, `Login.js`.
А также вызываются отображаются или скрываются модальные окна `EditProfilePopup.js`, `AddPlacePopup.js`, `EditAvatarPopup.js`, `ImagePopup.js` и `InfoTooltip.js`.
В `Main.js` в списке для отображения одного изображения используется `Card.js`.

##### Маршрутизация
Для настройки маршрутов используется библиотека `react-router-dom` \
С помощью него настраиватеся основная часть страницы с помощью Switch и Route
- "/" список изображений, компонент `Main.js`
- "/signup" страница регистрации, компонент `Register.js` 
- "/signin" страница авторизации, компонент `Login.js` 

##### Зависимости проекта
- react и react-dom для построения интефейса
- react-router-dom для маршрутизации
- react-scripts упрощение настройки для webpack
- testing-library и playwright для напиания тестов
- web-vitals - измерение метрик производительности
- dotenv - работа с переменными окружения
- wait-port - синхронизация запуска микросервисов

Управление состоянием реализовано через стандартный контекст React, который инициализируется в `CurrentUserContext.js`

##### Утилиты и вспомогательные функции
- `api.js` - класс, отвечающий за взаимодействие с бэкендом через REST api
-  `auth.js` - набор функций, отвечающий за авторизацию и аутентификации пользователей: регистрация, вход в систему, проверка токена

##### Стили и их организация
Стили организованы по методологии БЭМ (Блок, Элемент, Модификатор).
Расположены они внутри папки `./src/blocks`. Для каждого компонента своя папка, внутри папки для отдельных элементов внутри компонента, далее подпапки для отдельных состояний, если это необходимо. 

### 2. Разделние проекта на микрофронтенды и выбор паттерна декомпозиции

##### Этап 1. Предварительный анализ
Наше приложение Mesto достаточно простое и реализует следующие функции:
1. Загрузка и удаление фотографий
2. Отображение список фотографий
3. Сбор и учет лайков под фото
4. Создание профиля пользователя и его редактирование
5. Авторизация и аутентификация пользователя

Приложение уже написано на React и мы не планируем в ближайщем будущем переписывать какие-то его части на другой фреймворк.
Цель нашего перехода на микрофронты:
- разделить текущую команда разработки на несколько небольших команд, каждая из которых будет нести ответственность за свою часть функционала (один или несколько микрофронтендов)

##### Этап 2. Определение бизнес-функций, которыми будут заниматься разные команды
Основным методом разбивки нашего приложения на микрофронты я взял вертикальную нарезку.
В результате получаем:
- Host - основное приложение, которое обеспечивает каркас и загрузку микрофронтов
- Authorization - обеспечивает авторизацию и регистрацию пользователя
- Cards - обеспечивает отображение списка изображений, добавление и удаление изображений, учет и сбор лайков
- Profiles - обеспечивает отображение и редактирование профиля пользователя, аватара пользователя
Выделение Authorization и Profiles думаю не требует особых пояснений, очень легко выделяются в отдельные микрофронты и реализуют обособленную логику (аутентификация и авторизация) и (редактирование профиля пользователя)
Выделение всего функционала по работе с изображениями в одельный микрофронтенд, позволяет инкапсулировать всю логику работы с данной сущностью держать в одном месте. Также возможно имеет смысл вынести работу с лайками в отдельный микрофронтент, 
но это не было сделано, т.к. по работе с лайками сейчас очень мало функциональности. 
У нас бы получился в микрофронтенде с 1 компонентом и 1 методом api, поэтому решил оставить это на будущее.

##### Этап 3. Выбор метода реализации
Так как у нас предполагается несколько независимых команд, то выбираем runtime метод интеграции микрофронтов.
Метод композиции будем использовать клиентский. Пока в нашем приложении мы не задумываемся об оптимизации начальной загрузки и не хотели бы делать изменения на бэкенде в рамках нашего перехода на микрофронты, поэтому серверная и гибридная модель нам не подходят.

##### Этап 4. Выбрать инструмент для создания микрофронтендов
В качестве инструмента для работы с микрофронтами выбираем Webpack Module Federation. 
На мой взгляд он проще в использовании и поддерживает выбранный нами метод реализации.
Также не хотелось бы "подталкивать" команды к смене фреймворка в своем микрофронтенде выбрав Single SPA.

##### Этап 5. Настройка межмодульного взаимодействия
Приложение у нас достаточно простое, поэтому межмодульное взаимодействие будем через через API.
(т.е. каждый компонент получает обновления через свой бэкенд)

# Задание 2.

### Замечания
- Файл со схемой arch_task2.drawio лежит в корне репозитория рядом с README.md
- Пришлось немного добавить функций для портала электронной площадки, т.к. иначе некоторые сервисы просто "повисали в воздухе" и оказались не нужными после разбития на микросервисы

### 1. Основные бизнес-процессы решения
Перед нами системы для работы с торговыми площадками. \
Основные бизнес процессы:
- Управление пользовательскими аккаунтами
- Размещение товаров и услуг
- Работа с аукционами (создание и участие в аукционах других пользователей)
- Формирование и обработка заказов
- Учет и проведение транзакции за заказы
- Обеспечение поддрежки пользователей
- Оповещение пользователей об изменениях

### 2. Описание получившихся компонентов

1. **User Management (Управление пользователями и аутентификацией)**
    - Включает функции:
        - Регистрацию пользователя, аутентификацию
        - Присвоение ролей, хранение и валидация JWT
        - Управление профилем (редактирование контактных данных, статуса)
		- Формирование отчета об активности пользователей
    - Основные сущности: `Пользователь`, `Роль`, `Регистрационные заявки`
    - Компонент концентрируется на доступе и базовых данных о пользователях
	
2. **Nitification (Работа с нотификациями)**
	- Включает функции:
		- Рассылку различным оповещений
	- Основная сущность - Нотификация
	- Компонент отвечает за реализацию рассылки уведомлений
		
3. **Technical Support Request (Управление заявками на техподдержку)**
	- Включает функции:
		- Работа с заявками на техподдержку (создание, регистрация, обновление статуса)
	- Основная сущность - Заявка на техподдержку
	- Компонент отвечает за работу с заявками техподдержки
	
4. **Product (Управление каталогом товаров)**
	- Включает функции:
		- Поиск товаров
		- Фильтрация и сортировка результатов
		- Создание, редактирование и удаление товара
	- Основная сущность - Товар
	- Компонент отвечает за работу с каталогом товаров	
	
5. **Service (Управление каталогом услуг)**
	- Включает функции:
		- Поиск услуг
		- Фильтрация и сортировка результатов
		- Создание, редактирование и удаление услуги
	- Основная сущность - Услуга
	- Компонент отвечает за работу с каталогом услуг	

5. **Service (Управление каталогом услуг)**
	- Включает функции:
		- Поиск услуг
		- Фильтрация и сортировка результатов
		- Создание, редактирование и удаление услуги
	- Основная сущность - Услуга
	- Компонент отвечает за работу с каталогом услуг
	
6. **Auction (Управление аукционами)**
	- Включает функции:
		- Создание и редактирование аукциона
		- Обновление статуса аукциона
		- Обновление ставок аукциона
		- Обработка заявок на аукциона
	- Основная сущность - Аукцион
	- Компонент отвечает за создание и управление аукционами в системе
	
7. **Auction Appeal (Управление апелляциями по аукциону)**
	- Включает функции:
		- Создание и регистрация апелляции
		- Обновление статуса заявки на апелляцию
	- Основная сущность - Заявка на аппеляцию
	- Компонент отвечает за работу с заявками на апелляцию
	
8. **Order (Управление заказами)**
	- Включает функции:
		- Создание, редактирование заказа
		- Отображение заказа и его деталей
		- Изменение статус заказа (размещение, подтверждение)
		- Определение способа оплаты
		- Статистика и отчеты по заказам
		- Инициация платежной операции
	- Основная сущность - Заказ
	- Компонент отвечает за управление заказами
	
9. **Transaction (Хранение платежей и интеграция с внешними системами их обработки)**
	- Включает функции:
		- Работа с платежами (транзакциями)
		- Предоставление информации о платежах
		- Интеграция с внешними платежными системами TurboPay, FastMoney, Яндекс.Pay
	- Основная сущность - Тразакция
	- Компонент отвечает за интеграцию с платежными системами и хранение информации о платежах
